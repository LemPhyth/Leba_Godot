## 原程序的组织方式

代表性脚本显示，原作将逻辑分散在根时间轴动作、按钮事件、放置实例的 `load`、`keyDown`、`enterFrame` 事件，以及嵌套元件的帧动作中。大量代码通过 `_root` 全局变量、实例名和数字帧号互相调用。分析一个角色动作时，通常需要同时追踪输入事件、角色元件、碰撞子元件、技能界面和根状态。

以下入口构成初步的玩法定位图。数值只描述列出的实例或分支，不能推广成全游戏规则。

### 输入与移动

[根帧2中的角色逐帧事件](<C:/Users/24782/Desktop/leba_project/res/scripts/frame_2/PlaceObject3_6732_909/CLIPACTIONRECORD onClipEvent(enterFrame).as:2>)在角色当前帧不大于4时检测左右键37和39，每次事件把 `_x` 减或加6，改变 `_root.bug1` 与 `_xscale`，并播放动作第2帧。同目录其他事件对不同角色帧区段采用相似处理。

[角色内部按键事件](<C:/Users/24782/Desktop/leba_project/res/scripts/DefineSprite_6732/frame_1/PlaceObject2_4544_7/CLIPACTIONRECORD onClipEvent(keyDown).as:2>)将键码88（X）关联到角色第7帧；相邻事件把67（C）关联到另一动作区段。这里确认的是按键和帧的关系，尚未给全部动作建立名称、起止帧和可打断条件。

固定的“每次事件加6”与原作25 FPS 有关。迁移前应测量原作有效移动速度、暂停条件和事件执行顺序，再确定新工程的时间基准；不能仅把编辑器帧率改高而保留全部逐帧增量。

## 对下一步规划的影响

1. **先确定可玩切片，再追完整调用链。** 可以从已定位的角色元件、一个技能、一个敌人实例和根帧入口出发，整理输入、动作帧、碰撞、伤害、死亡和场景推进的完整链，并运行原游戏比对。具体职业与关卡待规划确认。
2. **保留原编号，再建立语义映射。** 为已选内容补充“角色或敌人—动作—起止帧—事件—资源ID”表。不要依据单张 PNG 或旧废案命名直接推断所有资源用途。
3. **区分画面快照与运行逻辑。** PNG 不执行 AS，也不能独立表达嵌套时间轴、命中判定与条件跳转。需要把原始锚点、变换、遮罩和动作事件一并纳入所选内容的分析。
4. **用小批量素材验证 Godot 导入。** Godot 4.6 会在导入时栅格化 SVG，复杂矢量和文本存在支持限制；不能据“SVG 能解析”推断其在 Godot 中完全一致。先验证代表性透明帧、遮罩、特效和字体，再决定运行时格式。[官方图像导入说明](https://docs.godotengine.org/en/4.6/tutorials/assets_pipeline/importing_images.html)
5. **把验收写成可观察的行为。** 首个切片至少要能比较移动距离、动作持续时间、MP消耗、有效命中、伤害、死亡和进度变化。原作25 FPS、时间轴异常和各实例的状态门控应进入比对条件。

当前可以进入范围与技术方案规划。剩余工作的核心是玩法语义映射、原作运行对照和 Godot 实现验证，而资源来源、原始结构及完整性证据已经可用。
